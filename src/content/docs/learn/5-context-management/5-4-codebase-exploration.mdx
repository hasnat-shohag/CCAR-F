## এই লেসনে যা জানতে হবে

বড় কোডবেস explore করা Claude-ভিত্তিক agent-এর সবচেয়ে context-ভারী কাজগুলোর একটি। অপরিচিত repository ঘাঁটা, dependency chain ট্রেস করা বা legacy সিস্টেম বোঝা — দীর্ঘ সেশনে একটি নির্দিষ্ট failure mode তৈরি হয়: **context degradation**। এটি টোকেন শেষ হয়ে যাওয়ার সমস্যা নয়। কনটেক্সট verbose discovery output-এ ভরে উঠলে মডেল আগের finding-গুলোর উপর দখল হারায়।

## Context Degradation

Context degradation-এর নির্দিষ্ট, লক্ষণীয় রূপ: সেশনের শুরুতে খুঁজে পাওয়া নির্দিষ্ট class, method ও dependency chain-এর বদলে মডেল "typical pattern" বলে উল্লেখ করতে শুরু করে। কয়েকটি module ঘেঁটে ফেলার পর agent বলতে পারে "this follows the typical repository pattern" — এর বদলে "the `OrderRepository` class at `src/repos/order.ts` implements the base `Repository<T>` interface with custom caching in the `findById` method."

কারণ:

- প্রতিটি exploration ধাপ প্রচুর output বানায় — ফাইলের কনটেন্ট, search result, directory listing।
- সেই output কথোপকথন context-এ জমতে থাকে।
- আগের নির্দিষ্ট discovery context-এ ধীরে ধীরে ভেতরে চলে যায়, আর সাম্প্রতিক verbose output প্রাধান্য পায়।
- মডেলের মনোযোগ সাম্প্রতিক output-এ সরে যায়, আগের finding-এর নির্দিষ্ট উল্লেখ হারিয়ে যায়।

মূল উপলব্ধি: **context degradation token limit-এর সমস্যা নয়।** Context window বাড়িয়ে এটি সারানো যায় না। মডেলের জায়গা শেষ হয়নি; নির্দিষ্ট খুঁটিনাটি নতুন, বেশি verbose output-এর নিচে চাপা পড়ে সে সেগুলোর হিসাব হারাচ্ছে।

## Scratchpad File

Context degradation-এর প্রধান প্রতিকার **scratchpad file**। Agent মূল finding একটি ফাইলে লেখে আর পরের প্রশ্নে সেই ফাইল দেখে। এতে জ্ঞান কথোপকথন context-এর বাইরে টেকে, আর context degradation থেকে নিরাপদ থাকে।

```markdown
# Exploration Scratchpad — Order Service

## Key Classes
- `OrderRepository` (src/repos/order.ts) — implements Repository<T>, custom findById caching
- `OrderService` (src/services/order.ts) — orchestrates OrderRepository + PaymentGateway
- `RefundProcessor` (src/services/refund.ts) — depends on OrderService.getOrderWithItems()

## Dependency Chain
RefundProcessor → OrderService → OrderRepository → PostgreSQL
RefundProcessor → PaymentGateway → Stripe API

## Critical Findings
- RefundProcessor has no retry logic for Stripe API failures
- OrderRepository caches by orderId but cache invalidation on status change is missing
- Test coverage: OrderService has 87% coverage, RefundProcessor has 12%
```

আগের discovery দেখতে হলে agent কথোপকথন context-এর বদলে scratchpad ফাইল পড়ে। এটিকে শুরু থেকেই ইচ্ছাকৃত কৌশল ধরুন, অবস্থা খারাপ হলে উদ্ধারের পদক্ষেপ নয় — কোনো দীর্ঘ exploration সেশনের গোড়া থেকেই agent-কে scratchpad ফাইল রাখতে নির্দেশ দিন।

## Subagent Delegation

নির্দিষ্ট investigation কাজে subagent তৈরি করা দ্বিতীয় প্রধান কৌশল। মূল agent নিজে সব exploration না করে (প্রতিটি ফাইল পড়া আর search-এর verbose output-এ নিজের context ভরে) নির্দিষ্ট প্রশ্ন subagent-কে দিন:

- "Find all test files for the order service and report their coverage status"
- "Trace the refund flow from API endpoint to database and list all intermediate services"
- "Identify all external API integrations and their error handling patterns"

প্রতিটি subagent নিজস্ব আলাদা context নিয়ে চলে। সে নির্ভয়ে verbose exploration করতে পারে, মূল agent-এর context নষ্ট না করে। সে coordinator-কে একটি structured summary ফেরায়, আর coordinator কেবল মূল finding-গুলো রাখে।

সমান্তরাল চালানোর সুবিধা চোখে পড়ে, কিন্তু আসল মূল্য **context isolation**। Subagent verbose exploration সামলালে মূল agent-এর context উচ্চ-স্তরের coordination-এর জন্য পরিষ্কার থাকে।

## ধাপের মাঝে Summary Injection

Exploration ধাপে ধাপে হলে (Phase 1: architecture বোঝা, Phase 2: নির্দিষ্ট component যাচাই), Phase 2-এর subagent তৈরি করার আগে Phase 1-এর মূল finding সারসংক্ষেপ করুন। সেই সারসংক্ষেপ Phase 2 subagent-এর প্রাথমিক context-এ ঢুকিয়ে দিন।

এতে "cold start" সমস্যা ঠেকায় — Phase 2 subagent আগের finding না পেয়ে Phase 1-এর exploration দুবার করে না। তাছাড়া Phase 2 agent-দের সঠিক প্রশ্ন করার মতো architectural বোঝাপড়াটুকুও মেলে।

```text
Phase 1 Summary (injected into Phase 2 subagent prompts):
- The system follows a layered architecture: Controllers → Services → Repositories → Database
- The refund flow passes through: RefundController → RefundProcessor → OrderService → PaymentGateway
- Key concern: RefundProcessor has no retry logic for external API failures
- Phase 2 objective: Investigate error handling in RefundProcessor and PaymentGateway
```

## /compact কমান্ড

Claude Code-এ দীর্ঘ সেশনে context ব্যবহার কমাতে `/compact` কমান্ড আছে। Verbose discovery output — ফাইলের কনটেন্ট, search result, directory listing — context ভরালে `/compact` কথোপকথন সংক্ষেপ করে জায়গা খালি করে, মূল তথ্য রেখে দেয়।

দীর্ঘ exploration সেশনে `/compact` সক্রিয়ভাবে ব্যবহার করুন, কেবল context limit-এ ঠেকলে নয়। এটি context-এর গুণ রক্ষার জন্য, কেবল পরিমাণের জন্য নয়।

## State Manifest দিয়ে Crash Recovery

দীর্ঘ exploration session crash, network interruption বা context exhaustion-এ ব্যর্থ হতে পারে। পুনরুদ্ধারের উপায় না থাকলে সব exploration অগ্রগতি হারিয়ে যায়।

সমাধান — structured state persistence। প্রতিটি agent নিজের বর্তমান অবস্থা একটি পরিচিত ফাইল অবস্থানে export করে (manifest)। এই manifest-এ থাকে:

- কী কী explore করা হয়েছে (পড়া ফাইল, চালানো search)
- এ পর্যন্ত পাওয়া মূল finding
- চলতি phase ও পরের ধাপ
- ঝুলে থাকা প্রশ্ন বা অমীমাংসিত বিষয়

```json
{
  "sessionId": "explore-order-service-001",
  "phase": 2,
  "exploredPaths": [
    "src/repos/order.ts",
    "src/services/order.ts",
    "src/services/refund.ts"
  ],
  "keyFindings": {
    "architecture": "Layered: Controllers → Services → Repositories → DB",
    "criticalIssue": "RefundProcessor has no retry logic for Stripe API failures",
    "testCoverage": { "OrderService": "87%", "RefundProcessor": "12%" }
  },
  "nextSteps": [
    "Investigate PaymentGateway error handling",
    "Review RefundProcessor test files",
    "Check cache invalidation logic in OrderRepository"
  ]
}
```

আবার শুরু হলে coordinator এই manifest লোড করে agent-এর prompt-এ ঢুকিয়ে দেয়। আগের exploration আবার না করে agent যেখানে ছিল সেখান থেকেই চালিয়ে যায়।

## প্র্যাকটিস সিনারিও (নিজে উত্তর ভাবুন, তারপর খুলুন)

> একটি developer productivity agent অপরিচিত কোডবেস explore করছে। কয়েকটি module ঘাঁটার পর সে আগের পাওয়া নির্দিষ্ট class name ও dependency chain-এর বদলে "typical repository patterns" বলে উল্লেখ করতে শুরু করল। সবচেয়ে কার্যকর প্রতিকার কোনটি?

<details>
	<summary>উত্তর দেখুন</summary>

	**সঠিক উত্তর:** Agent-কে মূল finding লিখে scratchpad ফাইল রাখতে দিন আর পরের প্রশ্নে সেটি দেখতে দিন।

	**কেন বাকিগুলো ভুল:**

	- *Model context window বড় করা* — Context degradation token limit নয়; বড় window-ও verbose output-এ ভরে আগের নির্দিষ্ট finding চাপা পড়বে।
	- *নতুন context-এ সেশন আবার শুরু করে আরও efficient exploration* — জমানো জ্ঞান হারায়, আর efficient exploration-এর নির্দেশ সমস্যার মূল (verbose accumulation) স্পর্শও করে না।
	- *পুরো কোডবেসের structure শুরুতেই context-এ pre-load* — প্রাথমিক context আরও ভরে যায়, degradation ত্বরান্বিত হয়।

</details>
