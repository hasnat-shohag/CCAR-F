## System prompt

- গদ্য বর্ণনার চেয়ে **বাস্তব কোড উদাহরণ** জোরে। "পরিষ্কার variable নাম দিন" লেখার বদলে আগে/পরে কোড snippet দেখান।
- **Severity calibration:** কোনটি critical আর কোনটি minor, তার ২–৩টি উদাহরণ নির্দিষ্ট কোড snippet দিয়ে দিন। Calibration ছাড়া মডেল সব সমস্যাকে সমান গুরুত্ব দেয়।

System prompt সাজানোর ক্রম:

1. ভূমিকা ও প্রসঙ্গ (মডেল কে, কী করছে)
2. নিয়ম ও সীমাবদ্ধতা (কী করবে / কী করবে না)
3. Output format-এর স্পেসিফিকেশন
4. Calibration উদাহরণ (severity, tone, বিস্তারের মাত্রা)

মূল নিয়ম: আচরণ নিয়ন্ত্রণের সবচেয়ে সাশ্রয়ী উপায় system prompt — একটি প্রম্পট প্রতি রিকোয়েস্টে দোহরানোর বদলে সব কলে ছায়া ফেলে।

পরীক্ষার প্রিয় প্যাটার্ন: কেবল output কাঠামোর জন্য একটি টুল বানান (যেমন `extract_entities`), তারপর `tool_choice: {type: "tool", name: "extract_entities"}` দিয়ে force করুন। এতে রেসপন্স আপনার schema মেনেই আসে।

Prompt-ভিত্তিক JSON-এর বদলে `tool_use` কেন:

- schema যাচাই করে API, পরে প্রসেসিং করে নয়
- syntax error নেই — ভাঙা JSON, অনুপস্থিত ফিল্ড, বাড়তি ফিল্ড
- streaming-এর সাথে চলে (structured chunk)

## Structured output-এর schema ডিজাইন

- ডেটা না থাকতে পারে এমন ফিল্ড optional করুন বা `null`-সহ union ধরন দিন। required ফিল্ডে ডেটা না থাকলে মডেল schema মেটাতে **মান বানিয়ে ফেলে**।
- সীমিত পছন্দে `enum` দিন, freeform মান ঠেকাতে।
- Schema যতটা সম্ভব সমতল রাখুন — গভীর nesting extraction error বাড়ায়।
- প্রতি property-তে `description` দিন; এগুলোই মডেলকে দেখায় কী তুলে আনতে হবে।

**Fabrication ঠেকানোর নিয়ম:** ফিল্ডের সত্যিকারের মান না থাকতে পারে, তাহলে তাকে union ধরন দিন আর parent object-এর `required` array থেকে বাদ রাখুন। তাতে `null` ফেরত দেওয়ার অনুমতি মডেল পায়, তথ্য বানানোর নয়।

```json
{
  "type": "object",
  "properties": {
    "postcode": { "type": ["string", "null"] }
  },
  "required": ["order_id"]
}
```

ব্যাকরণে সাবধান: `nullable: true` হলো OpenAPI-র নিয়ম, JSON Schema-র নয়; আর `required` parent object-এ একটি array, প্রতি property-তে boolean নয়। এই দুই রূপের যেকোনোটিতে লেখা `input_schema` প্রত্যাখ্যাত হয়।

## Few-shot উদাহরণ

কখন: নির্দেশ একা অসামঞ্জস্যপূর্ণ output দিলে। Few-shot ঠিক যে ফরম্যাট ও যুক্তি প্রত্যাশা করছেন, তা দেখিয়ে দেয়।

- **২–৪টি উদাহরণই মিষ্টি জায়গা।** বেশি হলে কনটেক্সট খরচ বাড়ে; কম হলে edge case বাদ পড়ে।
- উদাহরণে শুধু input → output নয়, **যুক্তিও** রাখুন। উত্তরটি কেন ঠিক, তা দেখান।
- Edge case রাখুন — অন্তত একটি উদাহরণে সীমানার আচরণ থাকুক।
- উদাহরণ system prompt-এ রাখলে caching-এর সুবিধা; user message-এ রাখলে প্রতি-রিকোয়েস্টে বদলানো যায়।

**Diminishing returns:** ০ থেকে ২ উদাহরণে সবচেয়ে বড় লাভ। ৪ থেকে ৮-এ গিয়ে মান প্রায় বাড়েই না, কনটেক্সট খরচ বাড়ে।

## Prompt chaining

**স্কোপ নোট:** গাইড prompt chaining-কে Domain 1-এর Task Statement 1.6-এ রাখে (fixed sequential pipeline বনাম dynamic adaptive decomposition), Domain 4-এ নয়। এখানে দোহরানো হলো কারণ ধাপের মাঝে validation, TS 4.4-এর retry loop-এর স্বাভাবিক সঙ্গী — তবে পরীক্ষায় এটি Domain 1-এর ধারণা হিসেবে ধরা হবে।

প্যাটার্ন: ধাপ ১ (extract) → ধাপ ২ (validate) → ধাপ ৩ (format) → ধাপ ৪ (synthesise)।

- প্রতি ধাপের প্রম্পট ছোট ও এক-দায়িত্ব — প্রতি ধাপে নির্ভুলতা বাড়ে
- এগিয়ে যাওয়ার আগে মধ্যবর্তী ফল যাচাই করা যায়
- একটি ধাপ আবার চালাতে গেলে পুরো chain চালাতে হয় না
- ভিন্ন ধাপে ভিন্ন মডেল (খরচ কমানোর সুবিধা)

কখন chain আর কখন একটি প্রম্পট: কাজের আলাদা আলাদা ধাপ ও আলাদা দরকার থাকলে chain; কাজটি সংহত আর output format সোজা হলে একটিই প্রম্পট।

## রিট্রাই প্যাটার্ন — `retry-with-error-feedback`

Output যাচাইয়ে ফেল করলে ফেরত পাঠান: **মূল প্রম্পট + ব্যর্থ output + নির্দিষ্ট validation error**।

```
Original: "Extract all dates from this contract"
Failed output: { dates: ["2024-01-15", "next Tuesday"] }
Error: "dates[1] is relative ('next Tuesday'), not absolute.
        All dates must be ISO 8601 format."
```

মডেল দেখে কী দিয়েছিল, কী ভুল ছিল — আর নির্দিষ্টভাবে সংশোধন করতে পারে। কখনো শুধু "try again" বলবেন না; নির্দিষ্ট error সবসময় দিন।

## নিজের output নিজে review করার সীমা

একই session-এ একটি মডেল নিজের output ভালোভাবে review করতে পারে না। যে reasoning output বানিয়েছিল, তা থেকে যায় — তাই নিজের সিদ্ধান্তে সায় দেওয়ার দিকে ঝোঁক।

সমাধান: review-এর জন্য **আলাদা model instance** (নতুন কথোপকথন, শেয়ার করা history নেই)। Review করা instance কেবল output দেখে, যে reasoning তাকে বানিয়েছে তা নয়।

বড় input-এ: **প্রতি-ফাইল pass** (প্রতিটি ফাইল আলাদা বিশ্লেষণ) আর **cross-file integration pass** (ফলগুলো এক জায়গায় মেলানো)। এটাই attention dilution-এর প্রতিকার — সব এক pass-এ চালালে মডেল খুঁটিনাটি মিস করে।
