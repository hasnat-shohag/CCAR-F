## Tool Description ডিজাইন

কোন টুল কল করবে তা বাছাইয়ের প্রধান সূত্র tool description — টুলের নাম নয়।

Description-এ যা থাকা উচিত:

- টুলটি কী করে (এক বাক্যে)
- প্রত্যাশিত input ফরম্যাট ও সীমাবদ্ধতা
- কী ফেরত দেয় (রেসপন্সের আকৃতি)
- সীমানা শর্ত (কী করে **না**)
- কোন ধরনের প্রশ্নে এই টুল ট্রিগার হবে, তার উদাহরণ

ভুল বাছাইয়ের দুই ভিন্ন কারণ, আর সমাধানও উল্টো:

Description প্রথম সমাধান কেবল তখনই, যখন টুলকিট আগেই কাজ করার মতো আকারে আছে। **প্রতি agent-এ ৪–৫টির বেশি** টুল হলে কেবল decision complexity-র কারণেই selection পড়ে যায় — ২২টি description নতুন করে লিখলেও সেই সমস্যা হাতের নাগালে থাকে না। Few-shot example দিয়ে misselection সারানোর কথা গাইডে নেই; পরীক্ষায় এটি ভুল হিসেবে ধরা হয়।

<ExamTrap label="Diagnose before you fix">

ছোট টুলকিটে দুটি একরকম টুল = description-এর সমস্যা। অতিরিক্ত বড় টুলকিট = বিতরণের সমস্যা, আর description কত ভালো হোক তার সমাধান হয় না।

</ExamTrap>

## Schema ডিজাইন নিয়ম

- প্রতি agent-এর টুল সেট ছোট ও ভূমিকা-কেন্দ্রিক রাখুন।
- প্যারামিটারের নাম বর্ণনামূলক দিন — `customer_email`, `email` নয়; `order_date_range`, `range` নয়।
- কেবল সত্যিই বাধ্যতামূলক হলে parameter-কে required করুন। ডিফল্টসহ optional প্যারামিটার ঘর্ষণ কমায়।
- সীমিত পছন্দে `enum` ধরন দিন — freeform string-এর চেয়ে মডেলকে ভালো পথ দেখায়।

<ExamTrap label="পরীক্ষার মূল পয়েন্ট">

প্রতিবার একই নির্দিষ্ট কাঠামো দরকার হলে `tool_choice: {type: "tool", name: "extract_data"}`। ডকুমেন্টের ধরন অজানা আর কয়েকটি extraction schema-র যেকোনোটি খাটতে পারে, তখন `tool_choice: "any"` — মডেল নিজে টুল বাছলেও structured output নিশ্চিত থাকে।

Agentic loop-এর সঠিক ডিফল্ট `auto`; টুল কখন কল করবে আর কখন টেক্সট দিয়ে উত্তর দেবে — সেই স্বাধীনতা মডেলের থাকা দরকার।

</ExamTrap>

## MCP আর্কিটেকচার

তিন স্তরের মডেল: **Host ⊃ Client ↔ Server** — host অ্যাপ্লিকেশন client ধরে রাখে, client server-এর সাথে যোগাযোগ করে।

	monoColumns={[0]}

	rows={[
		['Host', 'client-এর জীবনচক্র সামলানো অ্যাপ্লিকেশন।', 'Claude Desktop, একটি IDE extension।'],
		['Client', 'host-এর ভেতরের connector, যা একটি server-এ যুক্ত হয়ে তার টুল কল রাউট করে।', 'ডেস্কটপ অ্যাপ প্রতি server-এর জন্য যে client ইনস্ট্যান্স বানায়।'],
		['Server', 'tool, resource ও prompt প্রকাশ করে।', 'একটি database connector, file system server।'],
	]}
/>

Protocol: **JSON-RPC 2.0**, stdio বা streamable HTTP-এর উপর।

Configuration ফাইল:

- `.mcp.json` — প্রজেক্ট রুটে, প্রজেক্ট-স্তরের MCP server (টিমের সাথে শেয়ার হয়)
- `~/.claude.json` — ব্যক্তিগত/গ্লোবাল MCP server (কমিট হয় না)

মূল নিয়ম: আগে community MCP server খুঁজুন। আপনার দরকার কোনো community server মেটাতে না পারলে তবেই custom server বানান।

## টুলের এরর হ্যান্ডলিং

Structured error metadata — পরীক্ষায় ধরা প্যাটার্নটি। এটি result content-এর ভেতরে রাখা application-স্তরের convention, MCP envelope-এর অংশ নয়; প্রোটোকলের `CallToolResult` কেবল `content`, `structuredContent` আর `isError` সংজ্ঞায়িত করে:

```json
{
  "errorCategory": "transient",
  "isRetryable": true,
  "description": "Rate limit hit; retry after 5 seconds"
}
```

	monoColumns={[0]}
	columns={['ক্যাটাগরি', 'অর্থ', '`isRetryable`']}
	rows={[
		['transient', 'timeout, সার্ভিস unavailable।', '`true` — একই কল আবার পাঠান।'],
		['validation', 'ভুল input।', '`false` — input ঠিক করে নতুন কল পাঠান।'],
		['business', 'policy ভঙ্গ।', '`false` — বিকল্প পথে যান।'],
		['permission', 'প্রবেশাধিকার নেই।', '`false` — যার অনুমতি আছে তার কাছে escalate করুন।'],
	]}
/>

কেবল `transient` retryable: প্রশ্নটি একটাই — এই কলটা আবার পাঠালে কাজ হবে কি না? বাকি সব ক্ষেত্রে আগে input, অনুরোধ বা কলার বদলাতে হবে। **"Not found" ইচ্ছাকৃতভাবে বাদ** — কিছু না পাওয়া একটি বৈধ শূন্য ফল, এরর নয়।

<ExamTrap label="সবচেয়ে জরুরি পার্থক্য">

<strong>Access failure</strong> (auth error, network timeout) → retry করুন বা escalate করুন। কিছু একটা ভুল হয়েছে।

<strong>Valid empty result</strong> (search-এ ০ ফল) → মেনে নিন। তথ্যের অনুপস্থিতিই এখানে উত্তর।

</ExamTrap>

বৈধ শূন্য ফলকে কখনো এরর ভাববেন না। Access failure কখনো চুপচাপ গিলে ফেলবেন না।

নির্বাচনের নীতিমালা: সবচেয়ে নির্দিষ্ট টুলটি বেছে নিন। ভেতরের লেখা খুঁজতে Grep, ফাইল খুঁজতে Glob, জানা ফাইল পড়তে Read। যে কাজে বিশেষায়িত টুল আছে, সেখানে Bash এড়িয়ে চলুন।

Edit যদি non-unique match-এ ব্যর্থ হয়: গাইডের পরীক্ষিত fallback **Read + Write** — পুরো ফাইল পড়ে সংশোধিত সম্পূর্ণ ফাইল লিখে দিন।

বর্তমান অবস্থা (১৪ আগস্ট ২০২৬ তারিখে যাচাই): লাইভ tools reference অনুযায়ী Claude আগে একটিমাত্র occurrence চিহ্নিত করার মতো লম্বা anchor string পাঠায়, অথবা `replace_all: true` সেট করে। পরীক্ষায় উত্তর দিন **Read + Write**; বর্তমান Claude Code-এ এই আচরণ চিনে রাখুন।
